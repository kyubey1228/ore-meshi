# 画面表示の高速化（2026-09-13）

## 実装

- ホーム・企業向けトップ・マイページ・募集詳細で、主要内容と補助情報の取得／表示を分離。
- 企業の各画面で共通ダッシュボード全体を取得せず、その画面に必要なデータのみ取得。
- 個人の履歴・プロフィール・お気に入り・招待集計の取得列とクエリ数を削減。履歴全件表示と閲覧権限は維持。
- 詳細投稿フォーム、カレンダー、作成後共有ダイアログを必要時に読み込む。スマホのダイアログにスクロール領域を確保。
- 分析イベントのHTTP／DB書き込みを一括化。通知・紹介・需要照合を並列化し、通知保存とメール送信の完了待ちは維持。
- 最近見た募集は公開情報だけのGET APIへ変更。ヘッダーとお気に入り統合の認証確認を共有。

簡単投稿のページ用JSは、作業開始時の既存ビルドと比較してgzip合計126,664 bytes → 29,810 bytes（約76%減）。`client-reference-manifest`に列挙されるJSの比較であり、共通ランタイムを含むブラウザーの全転送量ではない。

## 初回100msを目標にした追加対策

条件なしの`/meals`は、Nodeサーバー初期化時に公開読み取りモデルを準備する。ホームと一覧は同じ先読み結果を使う。最終実装では12件＋次ページ確認用1件だけを保持し、条件付き検索や2ページ目以降はDBで絞り込んだページを取得する。

- 20秒ごとに背景更新。成功した操作の後にも更新を要求し、処理中は有効な前回結果を使う。
- 計測開始時点から60秒を超えた古い結果は返さず、DBの再取得を待つ。障害時に100msを保証する仕組みではない。
- 期限を過ぎた募集・広告は読み取り時にも除外する。参加・承認のDB検証、個人情報のアクセス制限は維持。
- ログイン済みでも最初の公開カードを個人設定DB取得で待たせず、その後おすすめ順を反映。仮表示時の表示イベントは重複計測しない。

## ページネーションと起動準備の追加改善（最終実装）

- DBの`LIMIT 13 / OFFSET`で1ページ12件に分割。ページ数算出の全件COUNTは行わず、13件目で次ページを判定。新着日時＋IDでページ境界を安定させ、各ページ内だけをおすすめ順に並べる。全件を対象とするおすすめ順ではない。更新・新規投稿がページ移動の間に入った場合はOFFSETの境界が移動する。
- 前／次ページのリンクで検索条件を保持。クイック条件変更時は1ページ目へ戻る。検索条件・残席数・3時間以内の候補日判定をDBのページ分割前に適用する。
- 募集者、候補日、目的、承認済み参加数、スポンサー情報を一覧専用のパラメーター化SQLで取得。通常のPrismaクエリ／書き込み設定は変更しない。検証中に通知エラーが出た`relationJoins`プレビュー機能は採用していない。
- 起動時は募集13件と公開の入力候補・広告等を**1本のSQL**で用意。接続プールのセッション状態に依存しないよう全テーブルにスキーマ名を明示し、JSON内の日時はUTCとして復元する。
- 公開一覧を個別に取得した結果、起動用の統合結果、従来Prismaで取得した結果の一致を読み取り検証済み。公開DBの対象1件で`EXPLAIN ANALYZE`は実行0.34ms、計画0.847ms。ただし接続済みでも通信・プロトコルを含む取得は945msだった。DB実行時間とアプリから見た取得時間は同じではない。
- DBスキーマ／インデックス変更はなく、この変更のための`npm run db:deploy`は不要。

最終本番ビルド、ローカルから既存DBへ接続した1回の起動計測：

| 指標 | 結果 |
|---|---:|
| 起動時の先読み準備 | 2,503ms（中間実装5,678ms） |
| 起動後の初回・実カードHTML到着 | 108.2ms |
| 初回全応答受信 | 109.7ms |
| 続く4回の実カードHTML到着 | 10.2 / 8.3 / 7.1 / 8.6ms |

**厳密な初回100ms以内はこの最終計測では未達。** 100ms判定スクリプトも初回をFAILとしている。コールドスタートや回線を含む100msを保証せず、本番配置での追加計測が必要。起動準備と通常リクエストのDB待ちは分離して報告する。

同じ最終ビルドの隔離E2Eサーバー（既に他の画面にアクセス済み）では、認証が受理されたことを確認して計測。ログイン済みユーザーの実カードは初回34.7ms、続く4回5.1〜6.1ms。個人向けの並び替えを含む応答完了は約1.28〜1.31秒であり、この待ち時間を初回カード到着から分離している。
